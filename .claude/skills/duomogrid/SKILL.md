# DuomoGrid invariants

Each rule below is a mistake that looks fine on its own but breaks something elsewhere in the repo. Files are named so you can check the claim.

## 1. Auth: every data route guards its own prefix
- `installIngestGuard(app, prefix)` (`src/auth/guard.ts`) adds a `preHandler` hook **inside the route plugin that calls it**. Route plugins are registered without `fastify-plugin`, so the hook is encapsulated. The guard in `listings.ts` does **not** protect a new `src/routes/foo.ts`. Any new route that reads or writes user data must call `installIngestGuard(app, "/foo")` itself, and its test must cover the 401 and 503 cases.
- The prefix match is `url.startsWith(prefix)`, so `/listings-export` is guarded by the `/listings` guard, but `/listing/...` is not.
- The guard fails closed: an empty `INGEST_TOKEN` returns **503** and never lets the request through. Keep it that way. The token comparison uses `timingSafeEqual` with a length check first. Don't replace it with `===`.
- `/users` (template example) has **no guard** and is open to anyone who can reach the port. Never put product data behind it or copy its pattern for new routes.
- The desk (`web/src/api.ts`) sends `Authorization: Bearer <token>` on every call. The token lives in `localStorage` under `duomo.token`.

## 2. Wiring for a new API prefix
- `web/vite.config.ts` proxies only `/listings` and `/assumptions` to :3000. A new API prefix used by the desk must be added there too, or it 404s only in `npm run dev:web`.
- `/` serves `web/dist/index.html` only when `NODE_ENV !== "test"` and the file exists. Otherwise it returns `{ message: "Hello World" }`, and `test/routes/root.test.ts` depends on that. Static assets are only `/assets/*` and `/favicon.svg`. There is no SPA fallback.
- `web/dist`, `drizzle/` and `.env` are resolved **relative to the process cwd** (`path.resolve(...)`). The server must start from the repo root, or from `/app` in Docker. A new runtime directory needs a `COPY` in the `Dockerfile` production stage.
- The desk map loads its basemap from `https://tiles.openfreemap.org`. `src/plugins/security.ts` allows that host on `connect-src` and `img-src`, and `worker-src` includes `'self'` and `blob:`. Dropping those directives blanks the map. `img-src` also allows `IMAGE_HOSTS` (`src/domain/types.ts`: `pictures.immobilienscout24.de`, `mms.immowelt.de`) for the hotlinked photos and floor plans; add a host to that one constant and both `parseIngest` and the CSP follow. `web/src/Map.tsx` calls `setWorkerUrl` on the Vite `?url` of `maplibre-gl-worker.mjs`. Without that, the built page requests `/assets/maplibre-gl-worker.mjs`, which Vite does not emit.

## 3. The extension→server payload is a compatibility contract
- `extension/extract.js` sends `v: 1`, `listingKind: "sale" | "rent"`, `hausgeldEur`, `provisionPercent`, `provisionText`, `rentedOut`, and, when the exposé has them, `latitude`, `longitude` and `street`. `parseIngest` (`src/domain/ingest.ts`) accepts these **and** the canonical names (`offer`, `condoFeeEur`, `commissionPercent`, `commissionText`, `tenantOccupied`). Installed extensions update separately from the server, so never drop an alias. Add new fields to both sides.
- A point is stored only when both coordinates are in range. `0,0` is treated as missing. `locationPrecision` is `"exact"` or `"approximate"`. The server believes a client precision only when it is exactly `"approximate"`; anything else, or nothing, is `"exact"`, so installed extensions that send none keep working. The extension sends `approximate` when the portal hides the address: IS24 with `showFullAddress` false (the point is the quarter centre) and Immowelt unless the classified has a `Point` geometry and `isAddressPublished` is true (otherwise the point is the centre of a polygon). A client that sends no precision is trusted as exact, so a re-save from an old extension can relabel an approximate point as exact. Coordinates are not parsed with `parseDeNumber` / `looseNumber`: those read `"48.137"` as the German thousand 48137.
- Fields added after the first extension release are optional and listed in `EXTRA_KEYS` (`src/domain/ingest.ts`): `heatingSystem`, `energySource`, `parkingSpaces`, `parkingType`, `parkingPriceEur`, `bathrooms`, `bedrooms`, `availableFrom`, `listedAt`, `portalPreviousPriceEur`, `portalMarket*EurPerM2`, `description`, `details`. `parseIngest` returns which of them the body **carried**. A re-save that lacks a key keeps the stored value, so an extension that predates the field never blanks it; a save that carries the key, even as `null`, replaces it. Add a new optional field to `EXTRA_KEYS`, the `extras()` merge in `src/routes/listings.ts`, `ListingInput`, the schema, and the extension together. Unknown or out-of-range values are `null`, never `0`. `energySourceOf` (server) and `energySourceOf` (extension) are deliberate copies of one fuel mapping; change them together.
- `images` (`{ url, caption, kind: "photo" | "floorplan" }`, 40 at most) are **hotlinked**: the server stores the URL and never fetches it, and the desk loads it from the portal CDN with `referrerPolicy="no-referrer"`. `parseIngest` keeps only `https` URLs whose hostname is exactly one of `IMAGE_HOSTS`, without credentials; every other URL is dropped, never rewritten. IS24 marks plans `FLOORPLAN` in `galleryData`; Immowelt lists them under `medias.floorplans`. Images disappear when the portal delists the listing. Archiving copies would need a fetch, which the "No requests, no crawl" rule rules out (tracked in #26). `GET /listings` returns `listing.images: []` and a single `coverUrl` (the first photo, never a plan); only the detail route returns the list. `observations.raw_json` leaves `images` out.
- `description` (four texts, paragraphs kept, 6000 chars each) and `details` (label/value pairs, 40) are listing text as published. The extension **leaves these keys, and `images`, out** when nothing was found (a page whose section failed to load must not blank stored text), and `details` only takes `dt`/`dd` pairs tagged `is24qa-` on ImmoScout24. A body that carries `description: null` does clear it. `GET /listings` returns `description: null`, `details: []`, `images: []` and `descriptionFindings: null`; only `GET /listings/:id` and PATCH return them. Analysis sees the same input on both routes, so a score never depends on which route asked. `observations.raw_json` stores the body **without** `description`, `details` and `images`.
- `describeFindings` (`src/domain/describe.ts`) reads the description for facts and skips a sentence that says no, or only that something is possible or planned; a year pairs only with the verb in its own clause. Findings are shown, not scored, with one exception: `present()` hands the renovation year to `analyze()` as `yearRefurbished` when none is stored, and it can switch off the "Unrenovated building" flag. A stored year always wins, and no other finding reaches analysis. Findings are cached per stored description text (`findingsFor`), so a list load does not rescan every description.
- `parseDeNumber` (extension) and `looseNumber` (server) are deliberate copies of the same German number parser: `"465.000"` → 465000, `"1.234,5"` → 1234.5, `"auf Anfrage"` → null. Change them together.
- Unknown values fall back on purpose: `offerOf` → `"buy"`, `propertyTypeOf` → `"other"`, `sourceOf` → `"manual"`, an unknown state → `null`. `title` falls back to `"Listing"`. `features` is capped at 24 entries, `snippet` at 600 chars, and PATCH `notes` at 4000 chars.
- The extension only reads the exposé already open in the tab ("No requests, no crawl"). Don't add fetching, crawling, or results-page scraping to the extension, the server, or CI. `duomoExtract` is tested against the saved document in `test/extension/fixtures/`, not against a live portal.
- The extension is not compiled. release-please bumps `extension/manifest.json` `version` together with the package version (`0.1.5`, never `v0.1.5`). The release workflow zips `extension/` with `manifest.json` at the archive root, checks that the manifest version matches the tag, and uploads `duomogrid-extension-<version>.zip` to that GitHub release. If that upload fails after the release exists, re-run the workflow with the `extension-tag` input set to the tag. There is no extension edge build: the popup already stores any server URL, and `:edge` is the server image.
- The popup reads `body.created` from the POST response. POST returns **201 + `created: true`** for a new row and **200 + `created: false`** for an update.

## 4. Buy and rent never share a score
- For `offer === "rent"`, `parseIngest` stores the cold rent in **both** `priceEur` and `coldRentEur` (`coldRent ?? price`). Observation `priceEur` for a rental is therefore the monthly cold rent, not a purchase price.
- `analyze()` computes purchase costs, financing, `monthlyTotal`, `grossYield` and the score **only when `offer === "buy"`**. For rentals `score` is `null` and `verdict` is `"rent"`. The desk sorts by `score ?? -1` and shows "Rent" in place of a score. Giving rentals a number would mix them into the buy ranking, which the README says never happens.
- `cohortSummary` compares only rows with the same `offer`, the same folded city, the same `propertyType`, and living area within 0.7–1.3×. `rentAgainstBuy` returns `null` for non-buy subjects.

## 5. Current price lives in `observations`, not `listings`
- `listings` has **no price column**. A listing's price is the `priceEur` of its newest observation: `prices()` orders by `seenAt` desc and keeps the first per listing. Any feature that reads price must go through observations.
- `seenAt`, `createdAt` and `updatedAt` are `new Date().toISOString()` strings, and ordering relies on lexical ISO-UTC order. Don't store local times or another format.
- A new observation is written only when the price changed **or the previous one was null**. `prices().get(id) ?? null` can't tell "no observation" apart from "null price", so a listing with no known price gets a new observation on every save. Keep that in mind before "fixing" the dedup.
- Upsert identity is `(source, externalId)`, or else an exact `sourceUrl` longer than 8 chars. A re-ingest overwrites every extracted field but keeps `notes`, `status` and `createdAt`. Don't reset user notes or status on re-save.
- A re-save that includes both coordinates replaces the stored point, except that an incoming `approximate` point never replaces a stored `exact` one (a dragged or corrected pin). An exact point from the portal still replaces anything. A re-save with neither coordinate, or only one, keeps the stored point and its precision. A street is stored whenever the save includes one, with or without a point, and a save that omits the street keeps the stored street. A re-save cannot clear a point. `PATCH` can move it when both coordinates are in range (`locationPrecision` becomes `"exact"` only when the coordinates differ from the stored point; sending the same numbers back keeps the precision) or clear it with `clearPoint: true`. Either way street, notes, status, and `createdAt` stay unless the patch itself sets notes or status.
- `PATCH` can correct `livingAreaM2`, `plotAreaM2`, `rooms`, `city`, `district`, `state`, `propertyType`, `yearBuilt`, `energyClass` and `priceEur`. Only keys present on the body are written. An empty value stores `null`, except `city`, which stores `""`. A non-positive area, rooms or price is 400, as is a year outside 1600–2100, an unknown state, an unknown property type, or an energy class outside A+–H. `propertyType` cannot be cleared. Numbers are not parsed as German thousands, so `"92,5"` is 400. A changed price inserts one observation; the same price writes nothing. On a rental that observation's price is the cold rent, and `listings.coldRentEur` is updated so analysis uses it. `warmRentEur` and `condoFeeEur` stay as saved. `offer` is not editable. A correction does not move the point and does not clear the Bodenrichtwert. District band and score are recomputed from the corrected row. A later save from the exposé still overwrites these fields. `DELETE /listings/:id` removes that listing's observations and then the row. Pass is not delete.
- A Bavarian Bodenrichtwert is cached on the listing (`brw_status`, `brw_zone`, `brw_eur_per_m2`, `brw_stichtag`) and is not a score input. `brw_eur_per_m2` is a real number: `2.000` stays 2000 and `1,3` stays 1.3. It is never rounded, and a non-positive figure is not a value. `GET /listings` never calls the WMS. `GET /listings/:id` looks it up only when a point is stored and there is no usable cache. A failed lookup is not saved; the same point is not asked again for 30 seconds, and a different point is. Outside the layer is stored as `none` and the desk shows nothing. `Information gebührenpflichtig` is `unpublished` with a null €/m², never `0`. `parseBodenrichtwert` (`src/domain/bodenrichtwert.ts`) reads the `text/plain` body. Replacing or clearing the point clears that cache; a save that keeps the point keeps it. The EPSG:4326 bbox is latitude, then longitude. The Bodenrichtwert is still looked up at an approximate point, but a flag built on one carries an "approximate" caveat and is never `good`: only an exact point can yield "Asking price is under the plot's land value". A published value on a buy can add a flag. The flag names EUR/m² of land and, when the plot area is known, the two totals in EUR. It does not compare that land value with the asking price per m² of living area. A missing, paywalled, or non-positive value adds no flag and is never treated as `0`.

- A district sale band comes from `reference/ak-oga/immobilienmarktbericht-2025.csv` (AK OGA, Immobilienmarktbericht Deutschland 2025). It is not under `data/`, because that directory is the SQLite volume and is dockerignored. The production image copies `reference/ak-oga`. `matchDistrictBand` uses `fold()` against `Subkr_Name_kurz` for the latest `BERJ`, city first and district only if the city misses, and only when the state agrees. Buy apartments use `Abb_4_92`, buy houses use `Abb_4_55`. Rentals, other property types, `NA`, an unknown district, and a missing file show nothing. The band string is shown as published. It is not a score input and not the asking-price benchmark in `src/domain/reference.ts`. On a buy of the same kind it can add a flag that says "district sale band". A missing band adds no flag. Rentals get neither that flag nor the land-value flag, and `verdict` stays `"rent"`.

## 6. Analysis math: unknown stays `null`, never `0`
- If the state can't be resolved, `transferTaxEur` is null, and so are `extraEur`, `cashToCloseEur`, `loanEur`, `monthlyDebt` and `monthlyTotal`. `monthlyTotal` is set only when **every** part (debt, heating, condo fee, ground rent) is known. Otherwise only `monthlyPartial` is set. Turning a null into 0 silently flips flags ("Equity does not cover…", "Above the monthly budget") and scores.
- Exceptions that are intentional: a missing condo fee counts as 0 for `house`, ground rent counts as 0 unless `leasehold`, and a missing commission uses `fallbackCommissionPercent` with `commissionAssumed = true`.
- All EUR outputs go through `roundEuro`, and fees are computed from the **rounded** price. `test/routes/listings.test.ts` checks exact values: 465000 in HE → transfer tax 27900, notary 2% → 9300.
- Subscore base weights are 0.35/0.25/0.15/0.15/0.10, then renormalized over the `applicable` parts. Non-applicable parts get weight 0. A new subscore must set `applicable` correctly, or it skews every buy score.
- Leasehold caps the price subscore at 42, and its €/m² is never compared with freehold.
- State resolution order: listing → postal code (first two digits of `PLZ2`) → `assumptions.defaultState`. Ambiguous PLZ ranges are **left out on purpose**. Don't "complete" the table. Transfer-tax rates live only in `STATES` (`src/domain/types.ts`).
- City matching uses `fold()` (lowercase, ä→ae, ö→oe, ü→ue, ß→ss, strip non-alphanumerics). `BENCHMARKS` keys must already be folded (`muenchen`, not `München`). Benchmarks apply only to `propertyType === "apartment"`.

## 7. Assumptions round-trip through `normalizeAssumptions`
- They are stored as JSON under `settings.key = "assumptions"`. Both GET and PUT, and the listings route, must pass stored or incoming JSON through `normalizeAssumptions`. Old rows with missing fields pick up defaults, and invalid JSON falls back to `DEFAULT_ASSUMPTIONS`.
- A new assumption touches: `Assumptions` and `DEFAULT_ASSUMPTIONS` (`src/domain/types.ts`), `normalizeAssumptions`, the `Assumptions` type in `web/src/api.ts`, and `web/src/Assumptions.tsx`.

## 8. The desk's types are a hand-written mirror
- `web/src/api.ts` (`DeskListing`, `Assumptions`, `Flag`, `Subscore`) re-declares the server's `present()` output and `Analysis` by hand. `web/tsconfig.json` doesn't import `src/`, so **`make typecheck` won't catch a renamed or removed field**. Update both sides in the same change.
- `bodenrichtwert` on that payload is `null` when the listing has no point. With a point it is `unknown` until `GET /listings/:id` fills it, then `none`, `published`, or `unpublished`.
- `descriptionFindings` is `null` on the list and an object on the detail route, so the desk treats a row with `null` findings as not yet loaded and asks `GET /listings/:id` for it (`web/src/App.tsx`). `listing.description`, `listing.details` and `listing.images` are only filled there; `coverUrl` is on both.
- `districtSaleBand` is `null` when there is no band. Otherwise it is the published range (`name`, `stateName`, `year`, `band`, `kind`).
- Listing status values `open | visit | offer | pass` are spelled out in the PATCH handler, `ListingStatus`, and the filter list in `web/src/App.tsx`.

## 9. DB, migrations, tests
- Migrations in `drizzle/` run at startup through `ensureDb()` against the user's SQLite volume. The journal maps idx 2 → `0003_smiling_exodus` and idx 3 → `0003_adorable_hammerhead`, and there is no `0002`. **Never rename, renumber or edit an existing migration.** Change `src/db/schema.ts`, run `npm run db:generate`, and commit the new SQL plus the `meta/` snapshot.
- `getDb()` is a module singleton that **ignores the URL once open**. Each test must `await app.close()` (which calls `closeDb`) before the next `buildApp()`. Env vars like `INGEST_TOKEN` or `DATABASE_URL` must be set **before** `buildApp()`, because `@fastify/env` reads them once.
- `test/plugins/db.test.ts` proves migrations ran by calling `GET /users`. Removing the template `users` route means rewriting that test first. Keep migration `0000` and the `users` table either way.
- Read config through `app.config` (the INGEST_TOKEN guard reads it per request), not `process.env`. The one existing exception is `LOG_LEVEL` in `buildApp()`.
- The Docker build runs `npm ci --ignore-scripts`. A new native dependency must ship prebuilds (as better-sqlite3 does), because `node:26-slim` has no Python or node-gyp.

## 10. Language
- UI, flags, notes, code and docs are English. City names, titles and listing text from the portals stay exactly as published. Don't translate or "fix" them on ingest.
