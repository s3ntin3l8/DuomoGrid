# DuomoGrid invariants

Each rule below is a mistake that looks fine on its own but breaks something elsewhere in the repo. Files are named so you can check the claim.

## 1. Auth: every data route guards its own prefix
- `installIngestGuard(app, prefix)` (`src/auth/guard.ts`) adds a `preHandler` hook **inside the route plugin that calls it**. Route plugins are registered without `fastify-plugin`, so the hook is encapsulated. The guard in `listings.ts` does **not** protect a new `src/routes/foo.ts`. Any new route that reads or writes user data must call `installIngestGuard(app, "/foo")` itself, and its test must cover the 401 and 503 cases.
- The prefix match is `url.startsWith(prefix)`, so `/listings-export` is guarded by the `/listings` guard, but `/listing/...` is not.
- The guard fails closed: an empty `INGEST_TOKEN` returns **503** and never lets the request through. Keep it that way. The token comparison uses `timingSafeEqual` with a length check first. Don't replace it with `===`.
- `/users` (template example) has **no guard** and is open to anyone who can reach the port. Never put product data behind it or copy its pattern for new routes.
- The desk (`web/src/api.ts`) keeps the ingest token in `localStorage` under `duomo.token`. It sends `Authorization: Bearer <token>` only when that token is non-empty. In proxy mode (`GET /auth/session` returns `{ mode: "proxy" }`) it omits the header entirely — including `Bearer ` with an empty token — and it never sets the identity header. `GET /auth/session` is unguarded and returns only the mode, never listings or a username. `POST /auth/pair` is guarded with the prefix `/auth/pair`, not `/auth`, so the session probe stays open. It returns only the ingest token. The extension stores the origin of the tab it paired from, not a host the server guessed, and it sends `Authorization` on that call only when `/auth/session` says `token`. It still sends the bearer token on `/listings` and never sets the identity header. A new route that reads or writes user data still calls `installIngestGuard` itself.
- `TRUSTED_AUTH_HEADER` is off unless it names a real header (not `authorization`, `cookie`, `host`, `forwarded`, or `x-forwarded-*`) and `TRUST_PROXY` is an address list. A non-empty name that fails that check stops the server at boot. The guard then accepts that header only when the socket peer is in the list and the request has no `Authorization` header. `true` and a hop count do not count: those trust the peer unconditionally, so a direct caller could forge the header. An empty `INGEST_TOKEN` is still 503, proxy header or not. The identity header is set by the proxy, never by the desk or the extension.

## 2. Wiring for a new API prefix
- `web/vite.config.ts` proxies `/listings`, `/assumptions`, `/auth`, `/ai` and `/mcp` to :3000. A new API prefix used by the desk must be added there too, or it 404s only in `npm run dev:web`.
- `/` serves `web/dist/index.html` only when `NODE_ENV !== "test"` and the file exists. Otherwise it returns `{ message: "Hello World" }`, and `test/routes/root.test.ts` depends on that. Static assets are only `/assets/*` and `/favicon.svg`. There is no SPA fallback.
- `web/dist`, `drizzle/` and `.env` are resolved **relative to the process cwd** (`path.resolve(...)`). The server must start from the repo root, or from `/app` in Docker. A new runtime directory needs a `COPY` in the `Dockerfile` production stage.
- The desk map loads its basemap from `https://tiles.openfreemap.org`. `src/plugins/security.ts` allows that host on `connect-src` and `img-src`, and `worker-src` includes `'self'` and `blob:`. Dropping those directives blanks the map. `img-src` also allows `IMAGE_HOSTS` (`src/domain/types.ts`: `pictures.immobilienscout24.de`, `mms.immowelt.de`) for the hotlinked photos and floor plans; add a host to that one constant and both `parseIngest` and the CSP follow. `web/src/Map.tsx` calls `setWorkerUrl` on the Vite `?url` of `maplibre-gl-worker.mjs`. Without that, the built page requests `/assets/maplibre-gl-worker.mjs`, which Vite does not emit.
- A map pin carries the listing's score, so the pin's look is baked into its element: a pin whose score band moved is replaced, not repainted. The band comes from the server's own `verdict` (`web/src/mapModel.ts`), never from a threshold the desk re-derives; a rental has no verdict band and shows as `R`.
- A pin that is drawn away from the point it stands for must use `Marker.setOffset()`, never a CSS transform on the element. MapLibre adds the marker's offset into the drag delta (`_positionDelta = e.point.sub(this._pos).add(this._offset)`), so a pin moved with `setOffset` still lands on the coordinates the user dropped it on; a pin moved with a CSS transform does not, and the desk would save a point up to a pin's width away.
- A pin with its own element cannot be dragged with the arrow keys (MapLibre only binds that for the default marker), so `web/src/Map.tsx` moves it on the arrow keys itself, one screen pixel per press (ten with Shift), and writes the point when the key is released. Those keys must `stopPropagation()`: the map's own `keydown` pans 100 px and Shift+Arrow rotates it. Enter and Space are handled on `keydown` with `preventDefault`, and a repeat is ignored, because `Marker.setPopup` toggles on `keypress` and a `<button>` then synthesises a click that toggles again — two toggles leave the overlay closed. A click with `detail === 0` and no preceding key (a screen reader, or `element.click()`) must still toggle: stopping it without opening leaves the pin dead. A hover preview is a `Popup` and must be closed with `popup.remove()`; removing only its DOM node leaves the map listeners.
- MapLibre opens a marker's popup from the **map's** click event, so the pin must not carry its own click handler that also toggles: two toggles leave the overlay closed. The overlay's own button is the way to the detail view. A spread pin is drawn at `setOffset`, so the overlay's offset has to include that same shift or the card sits on the true point, away from the pin. The fan is capped (`FAN_CAP`) and a group past one ring uses a second ring inside that cap. Clustering for the spread uses `SPREAD_CLUSTER_RADIUS`, which is wider than twice the cap, so one fan cannot land on the next group.


## 3. The extension→server payload is a compatibility contract
- `extension/extract.js` sends `v: 1`, `listingKind: "sale" | "rent"`, `hausgeldEur`, `provisionPercent`, `provisionText`, `rentedOut`, and, when the exposé has them, `latitude`, `longitude` and `street`. `parseIngest` (`src/domain/ingest.ts`) accepts these **and** the canonical names (`offer`, `condoFeeEur`, `commissionPercent`, `commissionText`, `tenantOccupied`). Installed extensions update separately from the server, so never drop an alias. Add new fields to both sides.
- A point is stored only when both coordinates are in range. `0,0` is treated as missing. `locationPrecision` is `"exact"` or `"approximate"`. The server believes a client precision only when it is exactly `"approximate"`; anything else, or nothing, is `"exact"`, so installed extensions that send none keep working. The extension sends `approximate` when the portal hides the address: IS24 with `showFullAddress` false (the point is the quarter centre) and Immowelt unless the classified has a `Point` geometry and `isAddressPublished` is true (otherwise the point is the centre of a polygon). A client that sends no precision is trusted as exact, so a re-save from an old extension can relabel an approximate point as exact. Coordinates are not parsed with `parseDeNumber` / `looseNumber`: those read `"48.137"` as the German thousand 48137.
- Fields added after the first extension release are optional and listed in `EXTRA_KEYS` (`src/domain/ingest.ts`): `heatingSystem`, `energySource`, `parkingSpaces`, `parkingType`, `parkingPriceEur`, `bathrooms`, `bedrooms`, `availableFrom`, `listedAt`, `portalPreviousPriceEur`, `portalMarket*EurPerM2`, `description`, `details`, `images`. `parseIngest` returns which of them the body **carried**. A re-save that lacks a key keeps the stored value, so an extension that predates the field never blanks it; a save that carries the key, even as `null`, replaces it. Add a new optional field to `EXTRA_KEYS`, the `extras()` merge in `src/routes/listings.ts`, `ListingInput`, the schema, and the extension together. Unknown or out-of-range values are `null`, never `0`. `energySourceOf` (server) and `energySourceOf` (extension) are deliberate copies of one fuel mapping; change them together.
- `images` (`{ url, caption, kind: "photo" | "floorplan" }`, 30 photos and 10 floor plans at most, each kind capped apart so a gallery of photos never pushes the plans out) are **hotlinked**: the server stores the URL and never fetches it, and the desk loads it from the portal CDN with `referrerPolicy="no-referrer"`. `parseIngest` keeps only `https` URLs whose hostname is exactly one of `IMAGE_HOSTS`, without credentials; every other URL is dropped, never rewritten. IS24 marks plans `FLOORPLAN` in `galleryData`; Immowelt lists them under `medias.floorplans`. `parseIngest` also drops a URL with a port or longer than 2048 characters, and a save whose images were all refused keeps the stored ones (only an explicit empty list clears them). Images disappear when the portal delists the listing. Opening the desk asks the CDN for one thumbnail per visible row, which tells the CDN your address and which listings you saved; the referrer is withheld and rows load lazily, but that is the cost of not keeping copies. Archiving copies would need a fetch, which the "No requests, no crawl" rule rules out (tracked in #26). `GET /listings` returns `listing.images: []` and a single `coverUrl` (the first photo, never a plan); only the detail route returns the list. `observations.raw_json` leaves `images` out on every write, POST and PATCH.
- `description` (four texts, paragraphs kept, 6000 chars each) and `details` (label/value pairs, 40) are listing text as published. The extension **leaves these keys, and `images`, out** when nothing was found (a page whose section failed to load must not blank stored text), and `details` only takes `dt`/`dd` pairs tagged `is24qa-` on ImmoScout24. A body that carries `description: null` does clear it. `GET /listings` returns `description: null`, `details: []`, `images: []` and `descriptionFindings: null`; only `GET /listings/:id` and PATCH return them. Analysis sees the same input on both routes, so a score never depends on which route asked. `observations.raw_json` stores the body **without** `description`, `details` and `images`.
- Price history comes from `observations` plus the portal's undated earlier price (`src/domain/history.ts`, `priceHistoryOf`). The earlier price is never turned into an observation: it becomes the first, undated point, and only when it differs from the first saved price, so `seenAt` ordering and the save-dedup rule are untouched. `listings.portal_previous_price_eur` keeps the **first** value reported, and a value is only accepted while the desk has seen at most one price: the portal moves it on with every cut, so a later one is either already an observation or cannot be placed in time. It is also left out of the timeline when it equals any saved price. A step from the undated price has no date, so it never sets `lastChangeAt`. `priceHistory` (reductions, increases, total change, `daysOnMarket`) is on every row of the list and the detail; the list still sends at most 12 observations, the detail all of them. Days on market count from the portal's listing date when there is one (`startedBasis: "portal"`), else from the first save.
- `describeFindings` (`src/domain/describe.ts`) reads the description for facts and skips a sentence that says no, or only that something is possible or planned; a year pairs only with the verb in its own clause. Findings are shown, not scored, with two exceptions that `present()` hands to `analyze()`: the renovation year as `yearRefurbished` when none is stored (a stored year always wins; it can switch off the "Unrenovated building" flag), and the heating renewal year for the energy subscore's old-heating adjustment. No other finding reaches the score. The special levy and a leasehold named in the text also become flags in `analyze()`, which change no score. Findings are cached per stored description text (`findingsFor`), so a list load does not rescan every description.
- `parseDeNumber` (extension) and `looseNumber` (server) are deliberate copies of the same German number parser: `"465.000"` → 465000, `"1.234,5"` → 1234.5, `"auf Anfrage"` → null. Change them together.
- Unknown values fall back on purpose: `offerOf` → `"buy"`, `propertyTypeOf` → `"other"`, `sourceOf` → `"manual"`, an unknown state → `null`. `title` falls back to `"Listing"`. `features` is capped at 24 entries, `snippet` at 600 chars, and PATCH `notes` at 4000 chars.
- The extension only reads the exposé already open in the tab ("No requests, no crawl"). Don't add fetching, crawling, or results-page scraping to the extension, the server, or CI. The one exception is the popup's update notice: it asks `api.github.com` whether a newer release zip exists, at most once an hour, and it does not read a portal page. `duomoExtract` is tested against the saved document in `test/extension/fixtures/`, not against a live portal.
- The extension is not compiled. release-please bumps `extension/manifest.json` `version` together with the package version (`0.1.5`, never `v0.1.5`). The release workflow zips `extension/` with `manifest.json` at the archive root, checks that the manifest version matches the tag, and uploads `duomogrid-extension-<version>.zip` to that GitHub release. If that upload fails after the release exists, re-run the workflow with the `extension-tag` input set to the tag. There is no extension edge build: the popup already stores any server URL, and `:edge` is the server image. On Windows the unpacked extension does not auto-update. Replace the files in the same folder and click Reload. A new folder is a new extension, and the stored server does not follow it.
- The popup reads `body.created` from the POST response. POST returns **201 + `created: true`** for a new row and **200 + `created: false`** for an update. `POST /listings?updateOnly=1` is the opt-in auto-update, and it is a **price check**: it answers **204 with an empty body and stores nothing** when the listing is not saved yet; for a saved one it writes only a new price observation (when the page shows a positive price that differs from the stored one), a listing date it did not have, and the portal's earlier price while the desk has seen at most one price (rows without a price do not count as seen). Every other column is left alone, so a value a half-loaded page failed to read is never erased and a correction made by PATCH is never undone, and a null price never becomes an observation. The one exception is the price itself: a price corrected by PATCH is an observation too, so an auto-update that sees a different portal price records it as a new step, as a manual save would. The portal's price is authoritative. Opening an exposé must never save it. The popup's "Update saved listings when I open them" (`chrome.storage.sync` `autoUpdate`, off by default) lets `content.js` extract the open page and hand it to `background.js`, which POSTs it to the user's own server at most once per exposé per 10 minutes (keyed by the portal id, `source:externalId`, with the address as the fallback; the timestamps live in `chrome.storage.session`, because an idle MV3 worker loses its memory, and a second open while one is being sent is dropped). With the option off, `content.js` reads and sends nothing. The extension still only reads the exposé that is open; auto-update fetches no portal page.

## 4. Buy and rent never share a score
- For `offer === "rent"`, `parseIngest` stores the cold rent in **both** `priceEur` and `coldRentEur` (`coldRent ?? price`). Observation `priceEur` for a rental is therefore the monthly cold rent, not a purchase price.
- `analyze()` computes purchase costs, financing, `monthlyTotal`, `grossYield` and the score **only when `offer === "buy"`**. For rentals `score` is `null` and `verdict` is `"rent"`. The desk sorts by `score ?? -1` and shows "Rent" in place of a score. Giving rentals a number would mix them into the buy ranking, which the README says never happens.
- `cohortSummary` compares only rows with the same `offer`, the same folded city, the same `propertyType`, and living area within 0.7–1.3×. `rentAgainstBuy` returns `null` for non-buy subjects.
- The rent-versus-buy comparison (`rentVsBuy` in `src/domain/rent-vs-buy.ts`, called by `rentAgainstBuy`) never compares `monthlyTotal` with a rent, because the total contains loan principal, which is saving and not cost. Both paths spend the same fixed amount every month, the buyer's first month (the loan payment plus `monthlyRunning`, the owner's costs apart from the loan and the heating, which a renter pays too), for the whole horizon: the buyer invests the payment that is freed once the loan is repaid, and the renter pays the median cold rent of the saved rentals (only rentals within 0.7 to 1.3 times the living area) and invests the rest, starting from the cash the buyer put in. The horizon is capped at 50 years, a yearly rate of -100 percent or less is refused, and a leasehold with no stated ground rent leaves `monthlyRunning` unknown. It reports the unrecoverable cost (interest, running costs, closing costs and the return the equity would have earned), average rent, and net wealth after `horizonYears` for each path. `horizon` is `null` without a rent sample or when `monthlyRunning`, the loan or the cash to close is unknown, and it is never a score input. Selling costs are not counted, and running costs do not grow.

## 5. Current price lives in `observations`, not `listings`
- `listings` has **no price column**. A listing's price is the `priceEur` of its newest observation: `prices()` orders by `seenAt` desc and keeps the first per listing. Any feature that reads price must go through observations.
- `seenAt`, `createdAt` and `updatedAt` are `new Date().toISOString()` strings, and ordering relies on lexical ISO-UTC order. Don't store local times or another format.
- A new observation is written only when the price changed **or the previous one was null**. `prices().get(id) ?? null` can't tell "no observation" apart from "null price", so a listing with no known price gets a new observation on every save. Keep that in mind before "fixing" the dedup.
- Upsert identity is `(source, externalId)`, or else an exact `sourceUrl` longer than 8 chars. A re-ingest overwrites every extracted field but keeps `notes`, `status` and `createdAt`. Don't reset user notes or status on re-save.
- A re-save that includes both coordinates replaces the stored point, except that an incoming `approximate` point never replaces a stored `exact` one (a dragged or corrected pin). An exact point from the portal still replaces anything. A re-save with neither coordinate, or only one, keeps the stored point and its precision. A street is stored whenever the save includes one, with or without a point, and a save that omits the street keeps the stored street. A re-save cannot clear a point. `PATCH` can move it when both coordinates are in range (`locationPrecision` becomes `"exact"` only when the coordinates differ from the stored point; sending the same numbers back keeps the precision) or clear it with `clearPoint: true`. Either way street, notes, status, and `createdAt` stay unless the patch itself sets notes or status.
- `PATCH` can correct `livingAreaM2`, `plotAreaM2`, `rooms`, `city`, `district`, `state`, `propertyType`, `yearBuilt`, `energyClass` and `priceEur`. Only keys present on the body are written. An empty value stores `null`, except `city`, which stores `""`. A non-positive area, rooms or price is 400, as is a year outside 1600–2100, an unknown state, an unknown property type, or an energy class outside A+–H. `propertyType` cannot be cleared. Numbers are not parsed as German thousands, so `"92,5"` is 400. A changed price inserts one observation; the same price writes nothing. On a rental that observation's price is the cold rent, and `listings.coldRentEur` is updated so analysis uses it. `warmRentEur` and `condoFeeEur` stay as saved. `offer` is not editable. A correction does not move the point and does not clear the Bodenrichtwert. District band and score are recomputed from the corrected row. A later save from the exposé still overwrites these fields. `DELETE /listings/:id` removes that listing's observations and then the row. Pass is not delete.
- A Bavarian Bodenrichtwert is cached on the listing (`brw_status`, `brw_zone`, `brw_eur_per_m2`, `brw_stichtag`) and is not a score input. `brw_eur_per_m2` is a real number: `2.000` stays 2000 and `1,3` stays 1.3. It is never rounded, and a non-positive figure is not a value. `GET /listings` never calls the WMS. `GET /listings/:id` looks it up only when a point is stored and there is no usable cache. A failed lookup is not saved; the same point is not asked again for 30 seconds, and a different point is. Outside the layer is stored as `none` and the desk shows nothing. `Information gebührenpflichtig` is `unpublished` with a null €/m², never `0`. `parseBodenrichtwert` (`src/domain/bodenrichtwert.ts`) reads the `text/plain` body. Replacing or clearing the point clears that cache; a save that keeps the point keeps it. The EPSG:4326 bbox is latitude, then longitude. The Bodenrichtwert is still looked up at an approximate point, but a flag built on one carries an "approximate" caveat and is never `good`: only an exact point can yield "Asking price is under the plot's land value". A published value on a buy can add a flag. The flag names EUR/m² of land and, when the plot area is known, the two totals in EUR. It does not compare that land value with the asking price per m² of living area. A missing, paywalled, or non-positive value adds no flag and is never treated as `0`.

- A district sale band comes from `reference/ak-oga/immobilienmarktbericht-2025.csv` (AK OGA, Immobilienmarktbericht Deutschland 2025). It is not under `data/`, because that directory is the SQLite volume and is dockerignored. The production image copies `reference/ak-oga`. `matchDistrictBand` uses `fold()` against `Subkr_Name_kurz` for the latest `BERJ`, city first and district only if the city misses, and only when the state agrees. Buy apartments use `Abb_4_92`, buy houses use `Abb_4_55`. Rentals, other property types, `NA`, an unknown district, and a missing file show nothing. The band string is shown as published. It is not a score input and not the asking-price benchmark in `src/domain/reference.ts`. On a buy of the same kind it can add a flag that says "district sale band". A missing band adds no flag. Rentals get neither that flag nor the land-value flag, and `verdict` stays `"rent"`.

## 6. Analysis math: unknown stays `null`, never `0`
- If the state can't be resolved, `transferTaxEur` is null, and so are `extraEur`, `cashToCloseEur`, `loanEur`, `monthlyDebt` and `monthlyTotal`. `monthlyTotal` is set only when **every** part (debt, heating, condo fee, ground rent and, for a bought `house` or `multi`, maintenance, property tax and insurance) is known. Otherwise only `monthlyPartial` is set. Turning a null into 0 silently flips flags ("Equity does not cover…", "Above the monthly budget") and scores.
- Exceptions that are intentional: a missing condo fee counts as 0 for `house` and `multi`, ground rent counts as 0 unless `leasehold`, and a missing commission uses `fallbackCommissionPercent` with `commissionAssumed = true`.
- All EUR outputs go through `roundEuro`, and fees are computed from the **rounded** price. `test/routes/listings.test.ts` checks exact values: 465000 in HE → transfer tax 27900, notary 2% → 9300.
- Subscore base weights are 0.35/0.25/0.15/0.15/0.10, then renormalized over the `applicable` parts. Non-applicable parts get weight 0. A new subscore must set `applicable` correctly, or it skews every buy score.
- A parking space with a stated price (`parkingPriceEur`, read as a price per space, which the ImmoScout24 sample states as "je 10.000 EUR" for two spaces, and the flag says so and by how much the cash would differ if it is a total; `parkingSpaces`, one assumed when missing and flagged as assumed) is part of the same purchase, so `analyze()` charges transfer tax, notary, land register and commission on `price + parking`, adds it to `cashToCloseEur`, to the equity base and to the cost-load denominator, and shows it as its own line. It is never part of `priceEur`, the price per m², or the price subscore. A parking space with no stated price adds nothing, never `0`. Rentals ignore it.
- The fuel is decided **once** (`fuelOf` in `src/domain/analyze.ts`) and used for the heating rate, the energy adjustment and the flags, so they cannot disagree. The fuel the exposé names (`energySource`) wins; the combined `heating` label only stands in when none is named, and a named but unrecognised fuel is unknown (rate 0.12), not read from the label. Heat pump and geothermal, then night storage, electric, district heat, oil (`Öl` at the start of a word, so `Ölheizung` matches and `boiler` does not), biomass, biogas and gas are checked in that order, so "Fernwärme aus Gas" is district heat and "Biogas" is not fossil. The energy subscore takes **one** adjustment, never a stack: oil or night storage −12, else gas −8, else a heating renewal 30 or more years old (read from the description, `heatingReplacedYear`) −8 unless a heat pump or district heat is stated, else a heat pump or district heat +5. Because the label counts, a listing saved earlier with a gas, heat pump or district label re-scores when this ships, as one with an oil label always did. These flags change no score: price reduced, long on the market (portal date only, 120 days), the portal's own EUR/m² estimate, a special levy or a leasehold named in the text but not set. All of them are buy-only.
- A bought `house` or `multi` with no stated Hausgeld has none, so `analyze()` adds maintenance (`maintenanceEurPerM2Year` times living area times an age factor: 0.5 under 10 years, 1 under 30, 1.4 under 60, else 1.8, from the newer of `yearBuilt` and `yearRefurbished`, 1 when both are missing), `propertyTaxEurYear` and insurance (`insuranceEurPerM2Year` times living area) to the monthly total. `yearRefurbished` can be a year found in the description (`present()` fills it from `findings.renovatedYear`), so one sentence in the exposé can lower the upkeep, as it already feeds the unrenovated flag. A house in a WEG (a terraced house) does state a Hausgeld, and that already holds the reserve and the building insurance, so then maintenance and insurance are `null` and only the Grundsteuer, which a Hausgeld never contains, is added. Never add all three on top of a stated Hausgeld. Maintenance and insurance need a living area and are `null` without one, which keeps `monthlyTotal` null and `monthlyPartial` set. Apartments, plots and rentals get `null` for all three, and their totals are unchanged. They are not a score input except through the Affordability subscore. For a `multi` the property tax is the whole building's, and its rents are not netted against it (#39).
- `maxOffer()` (`src/domain/max-offer.ts`) finds the highest whole-euro asking price that still fits `monthlyBudgetEur` or still scores 65, by bisecting over `analyze()` with only `priceEur` changed, so taxes, commission, parking and equity stay as they are for the real listing. It relies on the monthly total and the score not rising as the price falls, so it starts at 10,000 EUR: below that the rounding of fees makes the cost load look lower than it is. It is `null` for a rental, and each price is `null` when it is unknown: no budget, a budget below the costs that do not depend on the price, a total that is unknown at every price (no state, a house without a living area), or a score that never depends on the price (no price reference). It is computed only for detail responses (`full` in `present()`: GET and PATCH of one listing) and is `null` on the list and in the ingest responses. The 65 is `WORTH_A_LOOK` in `analyze.ts`, shared with the verdict ladder. It is display only and feeds no score.
- `fixedYears` is the interest-fixed period (Zinsbindung). When there is a loan, `analyze()` reports `remainingDebtEur` after it (`remainingBalance` in `src/domain/reference.ts`; 0 when the period covers the whole term) and `refinanceMonthlyPlus1Eur` / `refinanceMonthlyPlus2Eur`, the payment on that debt over the rest of the term at the current rate plus one and two points. All four fields (with `fixedYears`) are `null` without a loan, with an unknown state, and for rentals, and the two payments are also `null` when nothing is left. They are display only and feed no score.
- Leasehold caps the price subscore at 42, and its €/m² is never compared with freehold.
- State resolution order: listing → postal code (first two digits of `PLZ2`) → `assumptions.defaultState`. Ambiguous PLZ ranges are **left out on purpose**. Don't "complete" the table. Transfer-tax rates live only in `STATES` (`src/domain/types.ts`).
- City matching uses `fold()` (lowercase, ä→ae, ö→oe, ü→ue, ß→ss, strip non-alphanumerics). `BENCHMARKS` keys must already be folded (`muenchen`, not `München`). Benchmarks apply only to `propertyType === "apartment"`.

## 7. Assumptions round-trip through `normalizeAssumptions`
- They are stored as JSON under `settings.key = "assumptions"`. Both GET and PUT, and the listings route, must pass stored or incoming JSON through `normalizeAssumptions`. Old rows with missing fields pick up defaults, and invalid JSON falls back to `DEFAULT_ASSUMPTIONS`.
- A new assumption touches: `Assumptions` and `DEFAULT_ASSUMPTIONS` (`src/domain/types.ts`), `normalizeAssumptions`, the `Assumptions` type in `web/src/api.ts`, and `web/src/Assumptions.tsx`.

## 8. The desk's types are a hand-written mirror
- `web/src/api.ts` (`DeskListing`, `Assumptions`, `Flag`, `Subscore`) re-declares the server's `present()` output and `Analysis` by hand. `web/tsconfig.json` doesn't import `src/`, so **`make typecheck` won't catch a renamed or removed field**. Update both sides in the same change.
- `bodenrichtwert` on that payload is `null` when the listing has no point. With a point it is `unknown` until `GET /listings/:id` fills it, then `none`, `published`, or `unpublished`.
- `descriptionFindings` is `null` on the list and an object on the detail route, so the desk treats a row with `null` findings as not yet loaded and asks `GET /listings/:id` for it (`web/src/App.tsx`). `listing.description`, `listing.details` and `listing.images` are only filled there; `coverUrl` is on both.
- `districtSaleBand` is `null` when there is no band. Otherwise it is the published range (`name`, `stateName`, `year`, `band`, `kind`).
- Listing status values `open | visit | offer | pass` are spelled out in the PATCH handler, `ListingStatus`, and the filter list in `web/src/App.tsx`.

## 9. DB, migrations, tests
- Migrations in `drizzle/` run at startup through `ensureDb()` against the user's SQLite volume. The journal maps idx 2 → `0003_smiling_exodus` and idx 3 → `0003_adorable_hammerhead`, and there is no `0002`. **Never rename, renumber or edit an existing migration.** Change `src/db/schema.ts`, run `npm run db:generate`, and commit the new SQL plus the `meta/` snapshot.
- `getDb()` is a module singleton that **ignores the URL once open**. Each test must `await app.close()` (which calls `closeDb`) before the next `buildApp()`. Env vars like `INGEST_TOKEN` or `DATABASE_URL` must be set **before** `buildApp()`, because `@fastify/env` reads them once.
- `test/plugins/db.test.ts` proves migrations ran by calling `GET /users`. Removing the template `users` route means rewriting that test first. Keep migration `0000` and the `users` table either way.
- Read config through `app.config` (the INGEST_TOKEN guard reads it per request), not `process.env`. The one existing exception is `LOG_LEVEL` in `buildApp()`.
- The Docker build runs `npm ci --ignore-scripts`. A new native dependency must ship prebuilds (as better-sqlite3 does), because `node:26-slim` has no Python or node-gyp.

## 10. Language
- UI, flags, notes, code and docs are English. City names, titles and listing text from the portals stay exactly as published. Don't translate or "fix" them on ingest.

## 11. AI extraction, chat, and MCP
- `src/routes/ai.ts` (`/ai`) and `src/routes/mcp.ts` (`/mcp`) both call `installIngestGuard` with their prefix.
- AI settings live in `settings.key = "ai"`. API keys are encrypted at rest via `app.encryption` (`serializeAiSettings`/`normalizeAiSettings` in `src/domain/ai.ts`) and masked in API responses (`toPublicAiSettings` returns `apiKeyPreview`, never the raw key). Saving an API key in the database requires `DB_ENCRYPTION_KEY` (`app.encryption.isEnabled`); without it, `PUT /ai/settings` refuses with 400 rather than storing plaintext. Keys seeded from `AI_API_KEY` in `.env` (`apiKeySource` of `"env"`) are never copied into the SQLite `settings` row, so `.env`-configured deployments can update provider/model/auto-extract without `DB_ENCRYPTION_KEY`. `validateAiBaseUrl` allowlists only `127.0.0.1`, `localhost`, `host.docker.internal`, `api.openai.com`, and `api.anthropic.com`, and requests set `redirect: "error"`.
- Cached LLM description extractions (`listings.llm_extraction_json`) carry `descriptionHash: descriptionDigest(descriptionJson)`. When the hash matches the stored description, `mergeExtractedFacts` fills only missing (`null` / `false`) fields on the `ListingInput` snapshot at read/analysis time (`present()`) and **never** overwrites portal-extracted or user-PATCHed values. When no valid LLM cache exists, `present()` falls back deterministically to `describeFindings()`.
- Both the in-desk chat (`POST /ai/chat`, which enforces `readOnly: true` inside `executeAgentTool`) and the MCP server (`POST /mcp` and `npm run mcp` via `src/mcp/stdio.ts`) share the deterministic tools in `src/mcp/tools.ts` (`simulate_analysis`, `compare_listings`, `get_listing`, `list_listings`, `generate_makler_inquiry`, etc.) so real-estate math is never estimated by the model.
